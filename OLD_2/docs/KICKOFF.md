# Kickoff prompts

Copy-paste material. One block per person. Everyone works in the same repo with
whatever tool they prefer; `CONTRACTS.md` and `make check` are what keep the
outputs compatible.

---

## For everyone, first message of a new session

> Read CONTRACTS.md, CLAUDE.md and README.md in this repo before doing anything.
> They are binding. Then read contracts/*.schema.json for the artifacts my role
> owns, and artifacts/examples/ for what conforming output looks like.
>
> Do not start writing code until you have told me, in under ten lines, what you
> are going to build and which artifact keys it will produce. Then wait.
>
> Rules that fail CI: all model calls go through trust/gateway.py call_model();
> no original column names after S1, only col_NNN; no faultNumber or
> fault_status under pipeline/; no chemistry vocabulary in prompt literals.
> Run `make check` before telling me a task is done.

## E — Trust Layer & UI (first session)

> Read CONTRACTS.md, CLAUDE.md and README.md. I am role E: I own
> trust/gateway.py, trust/decision_log.py, artifacts/decision_log.jsonl and the
> operator UI. trust/gateway.py and trust/decision_log.py already exist and
> work — read them first, do not rewrite them.
>
> My first task is the operator UI. Constraints:
> - It reads ONLY from artifacts/*.json. It never imports a pipeline stage and
>   never touches the dataset.
> - artifacts/examples/ holds conforming fakes of every artifact. Build against
>   those; the real ones do not exist yet and I am not waiting for them.
> - Single-page app, one HTML file plus a small local server if needed. Ugly and
>   working beats pretty and late.
>
> Four screens, in this priority order:
> 1. Sensor report — one row per column from semantics.json: inferred role,
>    confidence, epistemic_status. Clicking a row expands the evidence objects
>    behind it, showing method, value and window for each.
> 2. Data quality — dq_report.json. The batch trust_verdict must be the loudest
>    thing on the screen. Checks grouped by dimension, each showing whether it
>    came from a baseline check or a compiled rule, and for compiled rules the
>    operator's original rule_text.
> 3. Drift and diagnosis — drift_events.json and diagnosis.json. The numbered
>    steps in order, the ranked sensors with their contribution shares, the
>    critique section, and the uncertainties list.
> 4. Decision log — decision_log.jsonl as a filterable table, plus an egress
>    panel calling DecisionLog.egress_summary(): what left the machine, to which
>    model, how many bytes, how many raw rows (zero, structurally).
>
> Every inference, check and flag in the UI must be clickable down to the
> evidence object that produced it. That traceability is the single highest
> scoring feature in this project — build it first, style it later.
>
> Override: on any inference or diagnosis, the operator can accept, question or
> override. An override writes a decision_log entry of kind "override" AND
> updates the artifact's human_override / human_review field. It must visibly
> change state, not just log. Show the overridden value with the original struck
> through beside it.
>
> Plan it first. Tell me the file layout and the state model before writing code.

## C — Data Quality

> Read CONTRACTS.md and README.md. I own S5: artifacts/dq_report.json.
>
> Two halves. Baseline checks across completeness, validity, consistency,
> timeliness and sensor_health — these need no data to write, only the schema in
> contracts/profiles.schema.json for what a normal profile looks like. Include
> frozen-signal detection via longest_plateau and saturation detection.
>
> Second half: the rule compiler. An operator writes a sentence, call_model()
> turns it into an executable check, the operator approves it before it goes
> live. The compiled check records the original rule_text, who approved it and
> when.
>
> Every check carries fault_class: data_fault or process_candidate. The batch
> trust_verdict of "untrusted" must stop the pipeline. This distinction is a
> whole scoring criterion.
>
> Also build the fault injector for the demo: a function that takes a clean batch
> and freezes one signal, so we can show the system refusing to diagnose.

## D — Drift & Diagnosis

> Read CONTRACTS.md and README.md. I own S6 and S7: artifacts/drift_events.json
> and artifacts/diagnosis.json.
>
> S6: PCA with control statistics over the normal baseline. Per-signal
> contribution is mandatory, not optional — an aggregate anomaly score with no
> attribution scores zero. Plus a separate slow-drift detector over rolling
> windows for signals trending inside their normal range.
>
> S7: turn an event into numbered steps a non-specialist can read, then a
> critique pass that looks for alternative explanations, checks whether
> dq_report.json suggests a data problem instead, and lowers confidence when
> doubt remains. The uncertainties list is required.
>
> faultNumber lives only in eval/. My pipeline code must not contain the string.
> Build the baseline from normal-operation data selected in eval/, handed to
> pipeline/ as an artifact, never as a label column.
